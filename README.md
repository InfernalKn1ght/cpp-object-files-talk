# Представление объектного файла: C++, Rust, Zig

Репозиторий к докладу о представлении объектного файла в C++, Rust и Zig.

Здесь находятся исходные примеры на трёх языках, скрипты сборки и анализа ELF, данные эксперимента, автоматически генерируемые таблицы и графики для презентации.

Эксперимент проводится на x86-64 Linux с ELF. В итоговых таблицах сравниваются режимы `O2` и `O2g`.

## Структура

```text
src/{cpp,rust,zig}/
  5 эквивалентных программ:
  demo, generics, strings, errors, cabi

tests/cabi_main.c
  общий C-main для проверки совместимости с C ABI

scripts/
  toolchain.py
    команды сборки для C++, Rust и Zig,
    режимы, флаги и версии инструментов

  collect.py
    сборка программ, измерение времени и памяти,
    разбор ELF и запись результатов в CSV

  report.py
    агрегация результатов,
    генерация таблиц .tex/.md,
    sizes.csv и графиков .png

  demo.sh
    демонстрация readelf/nm/objdump

  cabi_test.sh
    проверка линковки C-main с объектами C++, Rust и Zig

  repro.py
    проверка воспроизводимости двух сборок

slides/
  исходник презентации Beamer

docs/talk_script.md
  текст доклада

results/
  результаты измерений и файлы,
  генерируемые scripts/report.py

Makefile
Dockerfile
```

## Быстрый старт

Нужны:

* `python3`
* GNU binutils: `readelf`, `nm`, `objdump`, `size`
* `clang++`
* `rustc`
* `zig`

Для построения графиков нужен `matplotlib`.

Основной цикл:

```bash
make build

make metrics RUNS=10

make report

make demo L=cpp M=O2g

make cabi

make repro

make slides
```

После `make metrics` появляются сырые результаты:

```text
results/metrics.csv
results/sections.csv
results/relocs.csv
```

После `make report` дополнительно создаются:

```text
results/table_sizes.tex
results/table_symbols.tex
results/table_time.tex
results/sizes.csv
results/summary.md
results/chart_sizes.png
results/chart_relocs.png
results/chart_time.png
```

Именно эти файлы используются для результатов в презентации. Скрипт `report.py` генерирует три LaTeX-таблицы, а также `sizes.csv` и графики.

Можно использовать контейнер:

```bash
docker build -t objfile .

docker run --rm \
  -v "$PWD/results:/work/results" \
  objfile
```

Пути к компиляторам можно переопределить через `CXX`, `RUSTC` и `ZIG`.

Дополнительные флаги передаются через `EXTRA_CXXFLAGS`, `EXTRA_RUSTFLAGS` и `EXTRA_ZIGFLAGS`.

## Режимы сборки

| Режим | C++      | Rust                       | Zig                         |
| ----- | -------- | -------------------------- | --------------------------- |
| `O0g` | `-O0 -g` | `opt-level=0, debuginfo=2` | `-O Debug -fno-strip`       |
| `O2`  | `-O2`    | `opt-level=2, debuginfo=0` | `-O ReleaseFast -fstrip`    |
| `O2g` | `-O2 -g` | `opt-level=2, debuginfo=2` | `-O ReleaseFast -fno-strip` |
| `Os`  | `-Os`    | `opt-level=s, debuginfo=0` | `-O ReleaseSmall -fstrip`   |

В исходных данных присутствуют все четыре режима: `O0g`, `O2`, `O2g` и `Os`.

Однако `scripts/report.py` по умолчанию формирует итоговые таблицы только для `O2` и `O2g`:

```bash
python3 scripts/report.py
```

Параметр `--modes` позволяет изменить набор режимов:

```bash
python3 scripts/report.py --modes O2,O2g
```

Для `sizes.csv` и соответствующих графиков используется режим `O2g` по умолчанию.

Общие условия эксперимента:

* x86-64 Linux;
* ELF;
* Rust с `codegen-units=1`, чтобы получать один `.o`;
* Zig с `-fllvm`;
* фиксированное окружение и версии компиляторов.

Точные команды сборки определяются `scripts/toolchain.py`.

## Метрики

Эксперимент измеряет свойства объектного файла, символов, релокаций и стоимость компиляции.

| Метрика             | Как используется                                                                  |
| ------------------- | --------------------------------------------------------------------------------- |
| Размер `.o`         | общий размер объектного файла                                                     |
| `.text`             | размер секции с машинным кодом                                                    |
| `.data + .rodata`   | суммарный размер изменяемых и константных данных, используемый в таблице размеров |
| `.debug_*`          | размер отладочной информации                                                      |
| `.eh_frame`         | размер данных для раскрутки стека                                                 |
| Число секций        | число ELF sections                                                                |
| Defined / undefined | число определённых и неопределённых символов                                      |
| Weak                | число weak-символов                                                               |
| Релокации           | общее число релокаций и типы релокаций                                            |
| `.text*` sections   | число отдельных секций кода                                                       |
| COMDAT groups       | число COMDAT-групп                                                                |
| Время               | сумма медиан времени компиляции по программам корпуса                             |
| Max RSS             | максимум пикового RSS по программам корпуса                                       |

`report.py` агрегирует данные по паре `(язык, режим)`. Для обычных числовых метрик значения суммируются по программам корпуса, а для `max_rss_kb` используется максимум.

Для таблицы времени дополнительно используется:

* время: сумма медиан;
* Max RSS: максимум;
* `.text*` sections и COMDAT groups: количество соответствующих структур;
* `undef`: число неопределённых символов.

## Что показывают таблицы

### Размер объектного файла

В текущем эксперименте:

| Language / mode |     total | `.text` | `.data+.rodata` | `.debug_*` | `.eh_frame` |
| --------------- | --------: | ------: | --------------: | ---------: | ----------: |
| C++ O2          |    14 232 |   3 653 |             164 |          0 |         720 |
| C++ O2g         |    53 640 |   3 653 |             164 |     21 344 |         720 |
| Rust O2         |    14 592 |   2 250 |             349 |          0 |         560 |
| Rust O2g        |    82 104 |   2 250 |             349 |     33 998 |         560 |
| Zig O2          |   311 256 | 105 851 |          43 793 |          0 |       9 432 |
| Zig O2g         | 4 311 752 | 333 163 |          63 637 |  2 182 518 |      13 600 |

Основное наблюдение для презентации: C++ и Rust имеют близкий общий размер в `O2`, тогда как Zig в данном корпусе заметно крупнее. При переходе к `O2g` размер возрастает у всех трёх языков, особенно у Zig.

### Символы, секции и релокации

| Language / mode | sections | def./undef. | weak | relocations | main type       |
| --------------- | -------: | ----------: | ---: | ----------: | --------------- |
| C++ O2          |       69 |       55/11 |    8 |          56 | `R_X86_64_PC32` |
| C++ O2g         |      132 |       95/11 |    8 |         571 | `R_X86_64_32`   |
| Rust O2         |       83 |        62/7 |    2 |          53 | `R_X86_64_PC32` |
| Rust O2g        |      141 |        91/7 |    2 |       1 242 | `R_X86_64_32`   |
| Zig O2          |       53 |       168/7 |    0 |       5 878 | `R_X86_64_PC32` |
| Zig O2g         |      112 |       765/8 |    1 |      69 823 | `R_X86_64_64`   |

Особенно заметен рост числа релокаций при добавлении отладочной информации.

Число секций также увеличивается у всех трёх языков.

### Время, память и структура объектного файла

| Language / mode | time, ms | Max RSS, MB | `.text*` sections | COMDAT groups | undef. |
| --------------- | -------: | ----------: | ----------------: | ------------: | -----: |
| C++ O2          |      535 |         177 |                12 |             8 |     11 |
| C++ O2g         |      546 |         178 |                12 |             8 |     11 |
| Rust O2         |      224 |         188 |                21 |             2 |      7 |
| Rust O2g        |      247 |         189 |                21 |             2 |      7 |
| Zig O2          |    4 457 |         214 |                 6 |             0 |      7 |
| Zig O2g         |   13 615 |         322 |                 6 |             0 |      8 |

Эти значения следует читать с учётом способа агрегации: время — сумма медиан по корпусу, Max RSS — максимум по программам.

## Основные выводы эксперимента

В режиме `O2` C++ и Rust дают близкий суммарный размер объектных файлов:

```text
C++   14 232 bytes
Rust  14 592 bytes
```

Для Zig соответствующее значение составляет:

```text
Zig  311 256 bytes
```

При включении отладочной информации размер увеличивается до:

```text
C++   53 640 bytes
Rust  82 104 bytes
Zig   4 311 752 bytes
```

При этом `.debug_*` в `O2g` занимает:

```text
C++     21 344 bytes
Rust    33 998 bytes
Zig  2 182 518 bytes
```

По структуре объектных файлов переход к `O2g` также приводит к заметному увеличению числа секций и особенно релокаций.

Число релокаций изменяется:

```text
C++    56 -> 571
Rust   53 -> 1 242
Zig  5 878 -> 69 823
```

По времени компиляции в данном корпусе:

```text
C++   535 ms  -> 546 ms
Rust  224 ms  -> 247 ms
Zig  4 457 ms -> 13 615 ms
```

Max RSS:

```text
C++   177 MB -> 178 MB
Rust  188 MB -> 189 MB
Zig   214 MB -> 322 MB
```

Эти числа описывают конкретный корпус программ и конкретные версии инструментов и не являются универсальными характеристиками языков.

## Совместимость с C ABI

В репозитории есть общий C-main:

```text
tests/cabi_main.c
```

и сценарий:

```text
scripts/cabi_test.sh
```

Он используется для проверки линковки C-кода с объектами, полученными из C++, Rust и Zig.

На уровне презентации общий вывод такой: C ABI является практической границей взаимодействия между этими языками.

## Проверка воспроизводимости

Для проверки воспроизводимости используется:

```text
scripts/repro.py
```

Скрипт сравнивает две сборки и их SHA-256.

При необходимости можно отдельно анализировать влияние путей в DWARF и использовать соответствующие механизмы remapping.

Результаты воспроизводимости являются отдельной проверкой и не входят в три основные таблицы `report.py`.

## Слайды и автоматическая генерация результатов

Основной источник чисел для презентации — `scripts/report.py`.

Он читает:

```text
results/metrics.csv
results/relocs.csv
```

и создаёт:

```text
results/table_sizes.tex
results/table_symbols.tex
results/table_time.tex
results/sizes.csv
results/summary.md
results/chart_sizes.png
results/chart_relocs.png
results/chart_time.png
```

Таблицы затем подключаются в Beamer через `\input{...}`.

Это позволяет не редактировать числовые значения вручную: после повторного эксперимента достаточно пересоздать `results/` и выполнить `make report`. Логика генерации таблиц находится в `report.py`.

## Работа линкера

Текущий автоматический отчёт не содержит финальной метрики размера исполняемого файла после `--gc-sections` или отдельного сравнения с LTO.

Вместо этого на уровне объектного файла используются прокси-метрики:

* число undefined-символов;
* число релокаций;
* число `.text*` sections;
* число COMDAT groups.

Они описывают структуру объектного файла, но не заменяют эксперимент с финальным исполняемым файлом и реальной линковкой.

## Ограничения

* Только x86-64 Linux и ELF.
* Корпус состоит из пяти программ на каждый язык.
* Результаты зависят от конкретных версий компиляторов и инструментов.
* Текущий эксперимент использует `clang++`, `rustc` и Zig с LLVM-бэкендом.
* Числа из таблиц нельзя автоматически переносить на другие версии компиляторов, архитектуры и операционные системы.
* Семантика языков различается, поэтому одинаковые исходные идеи не гарантируют одинаковую структуру объектного файла.
* Большое число релокаций или больший размер `.o` сами по себе не являются оценкой качества языка.

## Воспроизведение

Минимальный порядок:

```bash
make build
make metrics RUNS=10
make report
make slides
```

После этого презентация получает таблицы и графики из `results/`.

Для просмотра низкоуровневых данных полезны:

```bash
readelf -SW file.o
readelf -sW file.o
readelf -rW file.o

nm file.o
objdump -dr file.o
```

Для C++ mangling:

```bash
c++filt
```
